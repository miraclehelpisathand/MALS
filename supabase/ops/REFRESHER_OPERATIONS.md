# Refresher scheduler operations — draft, not installed

The task 5 migrations and cron job are **not deployed**. These steps describe a proposed independent monitor; do not activate it until security review, signed-in API testing and the complete deployment plan have passed. Confirm your Supabase plan, extension support, backup/restore and data-location requirements first. Never place credentials in Git, Vite variables, chat, logs or shell command history.

## What the monitor checks

The database job is designed to run at minute 17 every hour and use the Pacific/Auckland calendar day. `private.run_refresher_scheduler` is idempotent and records a heartbeat, assignment count and SQLSTATEs (not trainee details). The opt-in GitHub Actions workflow runs at minute 47, authenticates as a dedicated, low-privilege Supabase Auth account and calls `refresher_monitor_status`. The endpoint fails closed unless that account is explicitly allowlisted by a privileged database operator and has no LMS role, group membership, leadership or course assignments. Its aggregate response fails when the expected active cron job is absent or altered, no recent heartbeat exists (three hours), any per-qualification error occurred in the last 26 hours, pg_cron execution logging is disabled, or pg_cron logged a failure in the last 26 hours. Errors remain visible for 26 hours even if a subsequent run succeeds. Cron execution logging must be enabled; confirm retention is at least 26 hours. The in-app administrator view is not an alert.

This GitHub Actions workflow is for **development and testing only**. GitHub’s Actions terms state that Actions may only be used to develop and test applications; do not rely on this workflow as a production monitoring service without resolving the applicable terms and choosing an appropriate production runner or service. See https://docs.github.com/en/site-policy/github-terms/github-terms-for-additional-products-and-features#actions .

GitHub scheduled workflows execute **only on the default branch**, may be delayed, and can be disabled after inactivity. A failed run is visible in GitHub Actions, but email delivery depends on each operator's GitHub notification settings. GitHub cannot reliably alert if the workflow itself never runs, GitHub or the repository is unavailable, or nobody watches failures. The monitor sends a secret HTTPS heartbeat to a separately configured dead-man's-switch service only after a healthy check. Such a service must be provisioned and verified to alert when that heartbeat is missing before relying on automatic scheduling. Agree the alert destination and an owner/on-call backup; test delivery and escalation. This workflow is a starting point, not a complete independent alerting system.

## Chosen heartbeat service: Healthchecks.io

The user selected Healthchecks.io: its hosted service monitors missed pings, supports email alerts and advertises 20 checks free (verify current terms and any organisational/vendor requirements before signup). It reports processing and storing data in Germany. The monitor sends only an empty success ping, not learner records; the provider still sees the request and account/notification information. References: https://healthchecks.io/ and https://healthchecks.io/docs/faq/ . GitHub Actions limitations: https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#schedule . The user reports setting up Healthchecks.io, a dedicated Supabase monitor account, and the three GitHub Actions repository secrets `MA_HEARTBEAT_URL`, `MA_MONITOR_EMAIL` and `MA_MONITOR_PASSWORD`. The UID provided by the user belongs to an administrator and must not be allowlisted. The user supplied a second UID, verified read-only as a confirmed account with no roles, memberships, leaderships or assignments. The UID has not been allowlisted; the user confirmed the GitHub email/password secrets belong to this separate account, but their values cannot be independently inspected. The GitHub integration could not list secrets (HTTP 403), so the secret could not be independently verified. Check settings and alert delivery have not been independently verified, and the check is not connected to the application yet. Keep automatic refreshers disabled until the monitoring arrangements are agreed and verified.

Suggested starting settings: one-hour period and two-hour grace for the hourly GitHub check, adjusted after testing delays and agreed response times. Healthchecks.io does not alert for a newly created check until it has received its first ping. An unhealthy scheduler is detected on the next GitHub run; if GitHub failure notifications are missed, the separate missed-ping alert arrives after its period plus grace. Allow for these delays in the operating plan.

## Proposed setup, after deployment approval

1. Create a Healthchecks.io account and a check named, for example, “Miracle Academy refresher monitor”. Choose a **simple one-hour period and two-hour grace**, then configure and verify an email notification recipient and a backup owner. Adjust the grace period if operational testing shows unacceptable delays or false alerts. Keep the generated ping URL private: it is a bearer secret. Do not paste it into chat or commit it to Git. A new check will not monitor missed pings until its first success ping.
2. Create a **dedicated Supabase Auth user** for the monitor with a strong unique password. Do not assign it any LMS role, group, course, admin privileges, or service-role key. Record its actual Auth user ID using the dashboard. Disable interactive use/MFA policies only if compatible with an approved machine-account process; otherwise use a different authenticated monitoring approach. Configure credential rotation and an owner.
3. Using a privileged database operator, add only the verified monitor user's ID to `private.refresher_monitor_users`. The table has no client grants. To revoke, delete that row, revoke the user's sessions/credentials, and review logs. A database administrator must perform this operation, not an LMS user. Verify that the monitor account cannot see other users' data and cannot invoke the scheduler.
4. Configure GitHub Actions repository variables `MA_SUPABASE_URL` and `MA_SUPABASE_PUBLISHABLE_KEY` with the public HTTPS project URL and publishable/anon key, and `MA_MONITOR_USER_ID` with the verified monitor account UID. The monitor rejects login as any other account before calling the health RPC. Configure encrypted repository secrets `MA_MONITOR_EMAIL` and `MA_MONITOR_PASSWORD` for the dedicated account, and `MA_HEARTBEAT_URL` for the independent dead-man's-switch secret HTTPS URL. A failed or unhealthy check deliberately sends no heartbeat. Never print or share that URL. Never use an admin password, database password, service-role key or secret API key. The workflow uses only `contents: read` and does not persist checkout credentials.
5. After ensuring the workflow is on the default branch, set repository variable `MA_CERTIFICATE_MONITOR_ENABLED` to `true`. Trigger it manually once and confirm it fails while the cron job is absent. Ensure the operator actually receives the failure notification; provision the independent dead-man's-switch and test its missing-heartbeat alert, allowing for schedule delays.
6. After target-database security and rollback-only tests pass, a privileged database operator may install `install_refresher_cron.sql`. After the first successful scheduler run, trigger the GitHub workflow and confirm the heartbeat provider received its **first** ping; until then a new check is not armed. Verify the job's command, schedule, owner, database, execution logging and UTC schedule. The monitor function's owner must be able to see the scheduled job and its run details under pg_cron's access rules; test rather than granting broad privileges to the monitor user. Its first successful run should clear a missing-job/heartbeat alert. Test failure and recovery in a **separate test environment**: confirm a healthy ping arms the check, stop pings long enough to trigger the alert, and verify notification and on-call escalation. Run with fictional data until end-to-end and physical-device checks pass.

## Incident response

- **No heartbeat/job inactive:** inspect pg_cron status, ownership, logging, connection limits, database health and recent job failures. Do not blindly create a second job. The named job is intended to be unique.
- **Per-qualification error:** use the administrator health panel for non-personal SQLSTATEs and investigate server logs/authorised records. Correct the underlying problem; rerunning the function as an authorised database operator is idempotent. A successful later run does not erase the last 26 hours of error indicators.
- **Monitor failed to authenticate or reach Supabase:** check project availability, dedicated account and secret rotation; do not print credentials or grant administrator/service-role access as a shortcut.
- **Workflow did not run:** the separate dead-man's-switch must alert. Check GitHub Actions settings, default branch, schedules, repository inactivity and external-monitor configuration.
- Check affected learners' assignment due dates and access after recovery. Keep existing certificates and learning records; expiry and failures must not erase history. Verify restore from tested backups and document any manual remediation.
